# Release process

Every crate in this repository is released together, with one version number for
all of them. A release does four things at once:

- It sets the same version in every crate and in the workspace dependency table.
- It regenerates every crate's `CHANGELOG.md` from git history.
- It builds the `fusibile` binaries and publishes them as a GitHub release.
- It publishes every crate to crates.io, in dependency order.

Nothing is published until you choose it. The release workflow runs in dry-run
mode by default.

## Versioning

All crates share one `MAJOR.MINOR.PATCH` version, set under `[workspace.package]`
in the root `Cargo.toml`. Path dependencies between crates use the same version in
`[workspace.dependencies]`. `dist/release/bump_version.sh` rewrites those entries,
and the README dependency snippets, in one pass.

Each crate is tagged with its own name, so its history stays easy to read:

- `remotefs-v<version>` for the core library.
- `remotefs-ssh-v<version>`, `remotefs-smb-v<version>`, and so on for the backends.
- `fusibile-v<version>` for the command line program.

The install scripts and the Homebrew formula download the `fusibile-v<version>`
release, so that tag must exist for every fusibile release.

## Running a release

1. Open the Release workflow from the Actions tab.
2. Enter the version without a leading `v`, for example `1.2.0`.
3. Keep `dry_run` set to `true` to build everything and check the output without
   pushing or publishing anything.
4. Once the dry run looks right, run the workflow again with `dry_run` set to
   `false`.

A real run does these steps, in order:

1. Validates the version and sets it in every crate.
2. Regenerates the changelogs with `just changelog_all <version>`.
3. Checks that `Cargo.lock` changed only in the workspace member versions.
4. Commits `chore: release v<version>` and pushes it to `main`.
5. Builds `fusibile` for Linux (musl), macOS, and Windows.
6. Tags every crate, creates the `fusibile-v<version>` GitHub release with the
   binaries, the checksums, and both install scripts.
7. Publishes every crate with `just publish_all`.
8. Updates the Homebrew formula in the tap.

## Local checks

Run these before opening a release run:

```sh
just test_scripts        # release, change detection, and install script tests
just changelog_all       # regenerate every changelog without a version
just publish_all "--dry-run --allow-dirty"
```

The dry run of `publish_all` can stop at the first crate whose workspace
dependencies are not on crates.io yet. Cargo is expected to report that for an
unpublished version, so it is not a failure of the release itself.

## One-time setup

These settings live outside the repository and must be in place before the first
release:

- GitHub Pages is enabled for this repository, with the source set to GitHub
  Actions. The install scripts are served from
  <https://remotefs-rs.github.io/remotefs-rs/>.
- The repository secret `RELEASE_PAT` is a token with contents write access. The
  workflow uses it to push the version commit and the tags, and to create the
  GitHub release.
- crates.io trusted publishing is configured for each of the eleven crates, with
  the repository `remotefs-rs/remotefs-rs` and the workflow `release.yml`.
- The Homebrew tap `remotefs-rs/homebrew-fusibile` exists and is writable with
  `RELEASE_PAT`.

## Changelogs

Each crate's `CHANGELOG.md` is generated by git-cliff from the conventional commits
that touch that crate, bounded by that crate's tags. The configuration is in
`cliff.toml`. `just changelog_all` regenerates all of them, and
`just fusibile_release_notes <version>` previews the notes that the GitHub release
uses.

Commit messages must follow the Conventional Commits format, because the
changelogs and the release notes are built from them.
